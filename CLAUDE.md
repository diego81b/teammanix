# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

SaaS PWA per società sportive, multi-tenant. Monorepo senza workspace root: `apps/api` (NestJS 11, Fastify, MikroORM 6, Postgres 16) e `apps/web` (Nuxt 4 SPA con `ssr: false`, Nuxt UI 4, Pinia, `@nuxtjs/i18n` v10). Specifiche: `ANALISI.md`, `mockup/PROMPT-UI.md`, `mockup/ui`. Deploy: `README.md` (Coolify). Il codice è in inglese: identificatori, rotte API e URL web, schema DB, codici errore, commenti, titoli dei test, commit, issue e PR (glossario IT-EN in `docs/glossary.md`). L'italiano resta solo nei testi per l'utente (i18n, mail, pagine legali) e nelle specifiche (`ANALISI.md`, `mockup`).

## Metodo: TDD obbligatorio

Ogni funzionalità e ogni bug parte da un test che fallisce (rosso, codice minimo, verde, refactor). Livelli, convenzioni e checklist per fetta in `TESTING.md`.

- Regole di business (permessi per ruolo e ambito, isolamento tra società, validazioni, codici errore) come test prima del codice; poi store e composable web; poi UI.
- Logica in funzioni pure testate per prime; guard, componenti e middleware restano gusci sottili (esempi: `decideAccess` in `apps/web/app/utils/access.ts`, `outboxEnabled`).
- Un bug si riproduce prima con un test, nel livello più basso che lo cattura. Un e2e solo per un percorso critico nuovo.
- Chiusura lavoro: `npm test` in entrambe le app, `npm run typecheck` (api) e `npx nuxt typecheck` (web) puliti, `npm run test:e2e` se toccati i percorsi coperti. Riportare i fallimenti con l'output.

## Comandi

Ambiente di sviluppo (Docker, dalla radice): `docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build`. API su :3001 (`/api`), Postgres su localhost:5433 (utente e db `teammanix`, password `devpassword`). All'avvio applica migrazioni e seed. Web: `cd apps/web && npm run dev` (:5173).

Variabili d'ambiente: un file per app, nella cartella dell'app, mai nella radice. API: default di sviluppo versionati in `apps/api/.env.dev` (letti dal compose), valori personali o segreti in `apps/api/.env` (non versionato, sovrascrive `.env.dev`; modello `apps/api/.env.example`); il compose fissa solo `DATABASE_URL`, `PORT`, `NODE_ENV`, `STORAGE_DIR`. Web, stessa regola: default versionati in `apps/web/.env.dev`, personali in `apps/web/.env` (modello `.env.example`, solo `NUXT_PUBLIC_*`). Nuxt legge solo `.env`, quindi `.env.dev` lo carica `loadEnvDev` (`apps/web/env-dev.ts`, chiamata in `nuxt.config.ts`): riempie solo le variabili non definite, mai in produzione, `.env` e shell vincono. Dopo una modifica: API `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d api`, web riavvio di `npm run dev`. L'API non carica `.env` da sola: fuori da Docker le variabili vanno passate dalla shell.

`apps/api`:
- `npm run test:unit` (senza Docker, `src/**/*.spec.ts`), `npm run test:int` (Testcontainers, serve Docker, `test/*.int-spec.ts`), `npm run test:watch`
- singolo file o test: `npx jest --selectProjects unit -- token.service`, `npx jest --selectProjects integration -- club-invitations -t "nome del test"`
- `npm run typecheck`, `npm run build`
- Migrazioni (nel container, schema in `src/migrations`, con snapshot): `docker compose -f docker-compose.yml -f docker-compose.dev.yml exec api npm run migration:create`

`apps/web`:
- `npm run test:unit` (Vitest node, `tests/unit`), `npm run test:nuxt` (runtime Nuxt, `tests/nuxt`), `npm test` (entrambi), `npm run test:coverage`
- singolo file: `npx vitest run --project unit tests/unit/accesso.test.ts`; per nome: `-t "testo"`
- `npx nuxt typecheck`
- E2E: `npm run test:e2e` (Playwright su Chrome installato). Richiede API con `E2E_OUTBOX=1`, già acceso in `apps/api/.env.dev`. Gli e2e creano utenti con email uniche nel DB di sviluppo.

## Architettura backend

- **Tenant**: ogni entità di una società estende `TenantEntity` (`entities/tenant.entity.ts`), che porta `club` e un filtro MikroORM attivo di default e fail closed: senza `clubId` sulla richiesta la query lancia. I flussi senza tenant (registrazione, accettazione invito, job) usano `{ filters: false }` esplicito.
- **Auth** (`auth/jwt-auth.guard.ts`, guard globale): il JWT porta solo utente e società attiva (`sid`), mai i ruoli. A ogni richiesta il guard rilegge dal DB utente, versione dei token (`tv` contro `User.tokenValidFrom`, il cambio password invalida i token vecchi) e appartenenza, ricalcola i ruoli (`MembershipsService.context`) e imposta il filtro tenant. Decoratori in `common/decorators.ts`: `@Public`, `@WithoutClub`, `@AdminOnly`, `@CurrentAuth`, `@AuthLimit`. Ogni rotta nuova richiede una società attiva salvo marcatura esplicita.
- **Errori**: ogni errore ha `code` stabile in maiuscolo (`{ message, codice }`), compresi quelli di validazione (`INVALID_DATA`, in `create-app.ts`). Il frontend traduce per codice e non mostra mai `message`.
- **Ruoli**: `AccessRole` con ambito `club | activity | team`; `Person` (scheda anagrafica, giocatore o staff) è distinta da `User` (account) e collegata dopo l'accettazione di un invito. Moduli: `auth`, `club`, `invitations`, `roles`, `permissions`, `structure`, `people`, `certificates`, `storage`, `audit`, `mail`. Permessi (regola 14): modello e calcolo in `permissions/policy.ts` (funzioni pure, `can` con ambito), diff per persona salvato in `Membership` e modificato da `PUT /permissions/:userId`; gli endpoint di gestione sono ancora `@AdminOnly`, l'applicazione delle policy per ambito arriva quando staff e dirigenti hanno endpoint propri. Ultimo admin: lock pessimistico sulle righe admin in `detach`, `RolesService.remove` e disabilitazione. Un codice errore deve comparire come letterale `code: 'X'` nei sorgenti (lo cerca `tests/unit/i18n.test.ts`), mai passato come argomento a un helper.
- **Certificati medici** (`certificates/`, dato sanitario art. 9): per default solo tipo, emissione e scadenza; vale per tutte le squadre, conta la scadenza più lontana (`certificate.rules.ts`, funzioni pure; il certificato non vale per chi è solo staff, regola 11). Il file è facoltativo e attivabile per società (`Club.certificatesWithFile`, `GET/PATCH /club/current/settings`): upload binario grezzo su `PUT /certificates/:id/file` (PDF, JPEG, PNG, max 5 MB, tipo ricavato dai magic byte; parser Fastify in `create-app.ts`), metadati in `Document` (`entities/document.entity.ts`, `MedicalCertificate.document`; nuove categorie = nuovo valore di `DocumentCategory` con le proprie regole di accesso e audit) e contenuto in `StorageService` (`storage/`): cifrato AES-256-GCM dall'app con `STORAGE_ENCRYPTION_KEY` (obbligatoria in produzione, derivata da `JWT_SECRET` altrove), driver `StorageFileSystem` (sviluppo e test) e `StorageS3` (produzione, obbligatorio, qualunque servizio S3 compatibile, variabili `S3_*`). I test dei driver condividono `test/storage-contract.ts`; il driver S3 si prova con `adobe/s3mock` (l'immagine MinIO non è più su Docker Hub). L'eliminazione definitiva di una persona deve cancellare anche i suoi oggetti nello storage. Ogni lettura di elenco o file va in `AuditLog` (`certificate_read`, `file_certificate_read`), mai con il contenuto nel `meta`. Rosa e scheda persona espongono solo `certificato: {stato, scadenza}` senza audit.
- **Ciclo della stagione** (regole 7, 8, 9): `POST /seasons/:id/close` (solo attiva, audit `closed_season`) lascia aperte le iscrizioni, così la rosa storica resta leggibile. `CloningService` (`people/`): `POST /seasons/:id/clone` crea una bozza nella stessa squadra con le sole iscrizioni scelte in un unico flush (la scelta parte da `GET /seasons/:id/roster`, che esclude chiusi e disabilitati; stato azzerato a disponibile, eventi non copiati), `POST /enrollments/:id/promote` aggiunge l'iscrizione in un'altra stagione e chiude l'origine solo con `closeSource`. Una sola stagione attiva e una sola bozza per squadra (indici univoci parziali, `DRAFT_EXISTS`; una bozza si modifica o si attiva, non si cancella). Le giornate di squalifica residue si riportano nella slice delle squalifiche.
- **Mail** (`mail/`): testi per lingua in `texts.ts` (tipo x it/en/fr, i link puntano a `APP_URL`). Senza `BREVO_API_KEY` si scrive solo su log (in produzione l'avvio fallisce). Fuori produzione `MailService.outbox` tiene le ultime 200 mail, usata dai test integration (`tokenFromMail`) e, con `E2E_OUTBOX=1`, esposta su `GET /api/__test/outbox`.
- **Avvio**: `src/create-app.ts` (`createApp()`) monta l'app; i test integration la usano con `app.inject`, `test/helpers.ts` (`startEnvironment`, `newUser`) avvia Postgres e imposta l'ambiente prima dell'import. `NODE_ENV=test` alza i limiti di throttling.
- **Profili sport**: il seed (`src/seed/sport-profiles.ts`) carica solo codici (`code`, `positions`, `starterBench`, `maxStarters`, `modulesAvailable`), mai testi. Il frontend traduce `sport.<code>` e `position.<code>` (`tests/unit/i18n.test.ts` legge il seed e verifica le tre lingue). `Enrollment.position` è un codice del profilo dell'attività, validato (`INVALID_POSITION`); nella promozione verso un altro profilo quella ereditata cade a null se non è prevista. Terminologia per sport (Gara, Lezione) e tipi di sanzione: stessa regola, codici qui e testi nel frontend, da aggiungere con le fette 3 e 5.

## Architettura frontend

- **Sessione**: `stores/session.ts` tiene token JWT (24h, nessun refresh), utente e appartenenze in `localStorage` (`tm-session`), riallineati con `GET /auth/me` al primo avvio (`refresh`). `composables/useApi.ts` è l'unico client: aggiunge il Bearer, normalizza gli errori in `ApiError(message, status, codice)`, su 401 svuota la sessione e va a `/login`. `errorText(e)` produce il testo per l'utente.
- **Routing**: `middleware/auth.global.ts` delega a `decideAccess` (funzione pura, tabella delle pagine pubbliche e dei passaggi obbligati: nessuna società attiva porta a `/welcome` o `/select-club`, scheda da completare porta a `/complete-record`). Redirect post-login filtrati da `internalPath` (anti open redirect). Le pagine di amministrazione (`/structure`, `/people`, `/seasons`, `/invitations`, `/archive`) sono in `ADMIN_ONLY` dentro `decideAccess`: un non admin va a `/`. Layout: `auth`, `default`, `legal`.
- **Lingue**: `it` è l'origine (`i18n/locales/it.ts`), `en.ts` e `fr.ts` sono tipizzati `typeof it` (chiave mancante = errore di compilazione). Strategia `no_prefix`, rilevamento del modulo spento: la lingua la gestisce `plugins/language.client.ts`. Precedenza: `User.language` poi `localStorage tm-language` poi browser poi `it`. Il cambio autenticato fa `PATCH /auth/language`. Sintassi vue-i18n: evitare `@ | { }` nei testi, niente trattini lunghi. Un nuovo `code` API richiede `errors.codes.<CODE>` nelle tre lingue (lo verifica `tests/unit/i18n.test.ts` leggendo i sorgenti dell'API). Notifiche in-app (fetta 6): `type` + `params` dal backend, testo tradotto dal frontend.
- **Form**: tutti gli `UForm` usano `:validate-on="['change']"`. Con la validazione al blur, un campo in autofocus mostra l'errore, sposta il layout e fa perdere i click.
- **Test nuxt**: `$fetch` nel runtime di test intercetta solo URL relativi, quindi `baseApiRelative()` (`tests/nuxt/helpers.ts`) e endpoint finti con `registerEndpoint('/api/...')`; risposte d'errore come `new Response(JSON.stringify(body), { status })` perché `createError` sposta il body in `data`. I composable con `useI18n()` girano dentro `inSetup()`, e lo store da usare è quello ottenuto nello stesso contesto. Import da `@nuxt/test-utils/runtime`. Con un dev server acceso, `.nuxt` è in uso e il registro degli auto-import dei test resta vecchio: un composable nuovo si importa esplicitamente nel test.
- **Amministrazione (slice 2)**: composable per area (`useStructure`, `usePeople`, `useCertificates`, `useAccess`) sopra `useApi`, lettura con `useLoad`. Regole nelle util pure (`roster`, `season`, `person`, `certificate`, `permissions`, `invitation`, `roles`); pagine e modali sono gusci. Lo stato `expired` di un invito si deriva da `expiresAt` (l'API lascia `sent`).
- **E2E**: dopo `page.goto` usare `go()` (`e2e/helpers.ts`): in sviluppo i click prima dell'idratazione vanno persi.
